# Collective Orders v0.1 — compatibility gate

Status: implementation proposal; no production persistence, permissions, or billing changes.

## Verified current boundaries

- Data Entry `src/features/orders/TicketOrdersTable.tsx` already owns specialized seasonal ticket, wristband and pocketfolder order matrices.
- Its `src/types/orderMatrix.ts` and Firestore `ticketOrders` records accept only those three categories.
- `dns-shared-data/firestore.rules` enforces the same category allowlist and scopes `ticketOrders` writes by membership/organization/area.
- Faktura V2 reads `ticketOrders` and `ticketOrderLines` using `FirebaseOrdersBackend`, then adapts them into its Order domain.
- Faktura V2 handles price sources, confirmation revisions, billing sheets, payment and delivery metadata. DNS's official accounting is external.

## Decision

Collective procurement (e.g. DNS Teamjacke) is a **distinct domain**, not a fourth value added to `OrderMatrixCategory`. The existing matrix and Firestore permissions must remain unchanged. Data Entry will own order composition, catalog variants, supplier source references and organization allocation. Faktura will own subsidy policy, pricing, cost-sharing calculation, billing confirmations and revisions. No private accounting data belongs in the public `dns-shared-data` repository.

The `src/features/collective-orders/model.ts` pure source-validation boundary intentionally does not write Firestore or implement a pricing engine.

## Before enabling persistence

1. Identify a distinct scoped collection and authorization contract; add emulator rules tests for admin, partner scoped read/write, immutability after approval, and forbidden cross-organization access.
2. Reconcile canonical identity separately for ordering organization, billed organization, and delivery recipient.
3. Design stable order, item, variant and supplier-document IDs; preserve source revision and provenance.
4. Extend the Faktura V2 ingestion adapter behind its own tests; do not silently blend collective orders into the ticket-order query.
5. Validate quantities, supplier document reconciliation, policy revision, VAT handling, rounding and regional one-time logo charges.
6. Require explicit review and approval before any billing sheet becomes READY.
7. Verify CI and Firebase emulator test outcomes before merging. No import into live Firebase until approved.
